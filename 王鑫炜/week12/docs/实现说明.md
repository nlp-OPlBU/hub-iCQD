# 实现说明与答辩要点

## 作业一：为什么不能只让模型输出一个等级？

直接输出“高/中/低”容易出现字段不统一、规则优先级漂移和无法核对依据等问题。
本作业先用多模态模型完成“视觉识别”，输出场景、清晰度、危险物、堆物程度和可燃物情况，
再由确定的 Python 条件分支做“风险决策”。模型感知仍可能出错，程序统一规则并不能消除识别错误。

请求流程：浏览器相机/文件 → 预览 → FormData → FastAPI → 内容校验/旋转/压缩
→ Qwen-VL 图文请求 → 严格 JSON 校验 → 分级 → 网页展示证据和建议。

三个容易混淆的边界：

1. **非楼道不等于无风险**。前者表示输入不属于任务场景，后者表示照片里的楼道未见堆物。
2. **待复核不等于无风险**。模糊照片没有足够证据支持“无堆物”。
3. **风险等级不等于起火概率**。作业给的是规则标签，程序没有概率校准数据，不输出虚假的百分比置信度。

`/health` 只说明 Web 服务正常，`/api/config` 只做本地配置检查；二者都不代表模型认证/额度有效。
“实时”指拍照后发起一次在线判断，不是持续视频分析，延迟取决于图片、网络和供应商。

## 作业二：LangChain 到底负责什么？

`ChatOpenAI` 是模型适配器，可访问 Qwen 的 OpenAI 兼容接口，并不表示必须调用 OpenAI 托管模型。
`create_agent` 创建消息与工具执行循环；`@tool` 提供工具的函数名、参数 Schema 和说明。
模型输出 tool call，框架调用函数，把结果作为 tool message 放回上下文，然后模型决定修正 SQL 或回答。

与第11周显式按阶段调用模型相比，这里由模型决定何时查看表、校验和执行。
程序仍控制执行权限、预算与校验条件。提示词里的“不要写数据库”本身不能提供只读保证，
实际限制由数据库连接和 authorizer 实施。

关键业务例子：如果一张发票有 5 行明细，JOIN 后 `invoices.Total` 会出现 5 次。
再 `SUM(Total)` 会重复计数。应单独汇总发票头，或汇总明细的 `UnitPrice * Quantity`。
目录表 `tracks.UnitPrice` 不能回答历史销量或销售额。

离线回放验证的是工程流程：预设错误 SQL 真的报错，真实修正 SQL 真的得到结果。
它不检验模型自主选表、写 SQL、修 SQL，也不能据此报告模型准确率。

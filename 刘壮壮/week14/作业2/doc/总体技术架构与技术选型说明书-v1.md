# 1. 项目概述

## 1.1 项目背景

本项目计划构建一个个人使用的多模态 RAG（Retrieval-Augmented Generation，检索增强生成）系统。

用户可以通过网页上传 PDF 文档，系统调用 MinerU 云端解析服务提取文档内容，经过文本切分和向量化后，将数据存储到 Elasticsearch 中。

用户可以通过自然语言与知识库进行多轮问答。系统通过关键词检索和向量检索相结合的方式获取相关内容，再将检索结果、历史对话和图片等上下文交给大语言模型，生成带有来源引用的回答。

系统第一版以完整实现核心业务链路为主要目标，优先保证功能可用、架构清晰、数据可靠和后续可扩展性，不提前引入复杂的 Agent 或多智能体机制。

## 1.2 项目目标

第一版主要实现以下能力：

1. PDF 文件上传和管理。
2. PDF 异步解析与任务状态管理。
3. 多模态文档内容提取和存储。
4. Elasticsearch 混合检索。
5. 多轮对话和 RAG 问答。
6. 用户图片输入和模型视觉理解。
7. SSE 流式回答。
8. 回答来源引用及原始文档关联。
9. 系统健康检查和基础操作日志。
10. 文档、任务、对话和系统运行状态管理。

## 1.3 系统设计原则

### 1.3.1 简单优先

第一版优先实现完整业务流程，不引入暂时没有实际需求的复杂架构。

### 1.3.2 职责分离

不同组件承担明确职责：

- SQLite 负责业务数据和任务状态。
- Elasticsearch 负责全文检索和向量检索。
- Kafka 负责异步任务传递。
- Redis 不作为第一版必需依赖。
- LangChain 负责模型调用相关能力。
- Python 业务代码负责系统流程控制。

### 1.3.3 数据可靠性优先

考虑 SQLite、Kafka、Elasticsearch 和文件系统之间的数据一致性，保证任务可以恢复、重复消息可以安全处理、失败任务可以重新执行。

### 1.3.4 松耦合

模型调用、检索、文件管理、任务调度等模块保持相对独立，避免某个技术组件的变化影响整个系统。

### 1.3.5 渐进式扩展

第一版不实现复杂 Agent、多知识库、Reranker 等功能，但在模块边界上保留后续扩展空间。

# 2. 系统总体架构

## 2.1 总体架构

系统采用前后端分离架构，后端采用模块化单体应用，并通过独立 Worker 进程处理异步 PDF 解析任务。

系统整体由以下部分组成：

1. 前端应用层。
2. 后端业务服务层。
3. AI 应用与模型调用层。
4. RAG 检索层。
5. 异步任务处理层。
6. 数据存储层。
7. 第三方云端服务层。

| 组件 | 主要职责 |
|---|---|
| React | 前端页面和用户交互 |
| FastAPI | API 接口、业务请求处理、SSE |
| PDF Worker | 异步 PDF 解析任务执行 |

## 2.3 后端架构模式

第一版采用模块化单体架构。

FastAPI 和 PDF Worker 在同一台 Mac 设备上运行，但作为两个独立进程部署。

两者共享业务代码和 SQLite 数据库，但各自承担不同职责：

- FastAPI 负责接收请求、管理文档和任务、处理问答。
- PDF Worker 负责从 Kafka 获取解析任务并执行文档解析。

第一版不拆分成多个微服务。

# 3. 系统部署架构

## 3.1 部署环境

系统采用 Mac 本地应用环境、Linux 基础设施环境和第三方云端 API 服务相结合的部署方式。

| 部署位置 | 运行组件 |
|---|---|
| Mac 本地 | React 前端、FastAPI、PDF Worker、SQLite、文件系统、BGE |
| Linux 云服务器 | Kafka、Elasticsearch |
| MinerU 云端 | MinerU VLM API |
| DeepSeek 云端 | DeepSeek Flash API |

## 3.3 Mac 本地环境

Mac 负责运行主要应用逻辑。

部署组件：

- React 前端。
- FastAPI 后端。
- PDF Worker。
- SQLite 数据库。
- 本地文件存储。
- BGE Embedding 模型。

其中：

FastAPI 和 Worker 是两个独立进程。

SQLite 仅由本地应用访问，不通过网络共享方式提供给 Linux 服务访问。

BGE Embedding 在本地执行，避免每次文本向量化都依赖外部 Embedding API。

## 3.4 Linux 云服务器

Linux 服务器部署：

- Kafka。
- Elasticsearch。

Linux 服务器不直接访问 Mac 本地 SQLite 和文件系统。

Mac 本地 FastAPI、Worker 通过 SSH 加密隧道访问 Linux 上的 Kafka 和 Elasticsearch。

## 3.5 SSH 加密隧道

Mac 与 Linux 之间使用 SSH 本地端口转发。

主要用于：

1. Kafka 消息通信。
2. Elasticsearch 查询和索引写入。

应用程序连接本地转发端口，由 SSH 隧道将流量转发到 Linux 服务。

不建议将 Kafka 和 Elasticsearch 的管理端口直接暴露到公网。

## 3.6 云端 API 通信

FastAPI 和 Worker 根据业务需要分别调用第三方服务：

- MinerU：PDF 解析。
- DeepSeek：模型推理。

所有 API Key 由后端配置文件或环境变量管理，不向前端暴露。

与第三方服务之间使用 HTTPS 通信。

## 3.7 服务启动与依赖

应用启动时不主动执行全部第三方依赖检查。

系统通过健康检查模块提供后台定时检查和手动检查能力。

当 Kafka、Elasticsearch 或第三方 API 不可用时，相关业务操作应返回明确的错误状态，不应导致整个应用无法启动。

# 5. AI 调用架构

## 5.1 技术选型

第一版使用 LangChain 作为 AI 调用框架，DeepSeek Flash 作为统一的大语言模型。

| 项目 | 选型 |
|---|---|
| AI 框架 | LangChain |
| 模型提供商 | DeepSeek |
| 模型名称 | deepseek-flash |
| API 地址 | https://api.deepseek.com |
| 接口形式 | OpenAI 兼容接口 |
| 模型调用 | LangChain Chat Model |
| Prompt | 集中管理 |
| 输出处理 | Pydantic 结构化输出 |
| 流式处理 | 异步流式输出 |
| 超时与重试 | LangChain 配置 + 必要的业务异常处理 |

## 5.2 LangChain 的职责

LangChain 主要负责：

1. 模型调用接口封装。
2. Prompt 模板管理。
3. 模型输入消息组织。
4. 结构化输出处理。
5. 模型请求超时控制。
6. 模型调用失败重试。
7. 异步流式输出。

LangChain 不负责系统完整业务流程，也不直接决定是否执行 RAG 检索。

## 5.3 AI Application Service

AI Application Service 是问答业务的流程控制中心。

主要负责：

- 加载历史上下文。
- 调用 Query Rewrite。
- 调用 RAG Retrieval。
- 调用 Context Builder。
- 调用 Response Generator。
- 处理回答结果。
- 将回答转换成 SSE 事件。

具体流程由 Python 代码控制。

## 5.4 Query Rewrite

Query Rewrite 用于改善用户问题的检索效果。

输入：

- 用户原始问题。
- 必要的历史对话上下文。

输出：

- 改写后的检索问题。

要求：

1. 保留用户原始问题。
2. 只将改写结果用于检索。
3. 不要求所有问题都必须改变措辞。
4. 最终回答仍结合用户原始问题和历史上下文。
5. 不使用 Multi-Query。

第一版可以使用 Pydantic 约束改写结果格式。

## 5.5 Context Builder

Context Builder 负责组织交给模型的完整上下文。

包括：

- 用户原始问题。
- 最近的历史对话。
- 历史摘要（如果已经生成）。
- Elasticsearch 检索结果。
- PDF Chunk 内容。
- PDF 来源信息和页码。
- PDF 提取图片。
- 用户本轮上传的图片。

Context Builder 由自己的 Python 业务代码实现，不将数据组织完全交给 LangChain。

## 5.6 Response Generator

Response Generator 负责最终回答生成。

主要工作：

1. 接收 Context Builder 组织好的上下文。
2. 使用回答 Prompt。
3. 通过 LangChain 调用 DeepSeek Flash。
4. 获取模型流式输出。
5. 将模型输出转换成业务层可处理的流式事件。

最终回答应支持文本和图片相关内容的理解，并保留 PDF 来源引用。

## 5.7 模型超时与重试

模型调用应设置超时和有限次数重试。

建议第一版采用：

- 普通模型请求超时：默认 60 秒，可按调用类型调整。
- 最大自动重试：默认 2～3 次。
- 重试间隔：指数退避，可加入随机抖动。
- 连接异常、临时服务错误和限流：根据异常类型决定是否重试。
- API Key 错误、参数错误等不可恢复错误：不重复重试。

需要注意：

流式回答已经向前端发送部分内容后，如果发生连接中断，不能简单从头重试并继续发送，否则可能产生重复内容。

因此，流式生成的重试边界需要单独处理。

## 5.8 Agent 使用策略

第一版不使用自主 Agent 执行循环。

不使用：

- OpenAI Agents SDK。
- LangChain Agent。
- LangGraph。
- Multi-Agent。

原因：

第一版 RAG 流程已经明确，所有问题均执行检索，执行顺序由 Python 业务代码控制。

当前没有让模型自主规划工具和执行复杂任务的必要。

未来确实需要模型自主调用多个工具、规划任务或执行复杂工作流时，再评估引入 Agent 或 LangGraph。

# 6. RAG 检索架构

## 6.1 技术选型

| 模块 | 技术 |
|---|---|
| 向量模型 | BAAI/bge-small-zh-v1.5 |
| 向量存储 | Elasticsearch |
| 全文检索 | Elasticsearch BM25 |
| 向量检索 | Elasticsearch Dense Vector |
| 混合检索 | BM25 + Dense Vector |
| 结果融合 | RRF |
| Reranker | 第一版不使用 |

## 6.2 检索流程

```text
用户原始问题
      |
      v
Query Rewrite
      |
      v
生成检索向量
      |
      +----------------------+
      |                      |
      v                      v
BM25 关键词检索         Dense Vector 检索
      |                      |
      +----------+-----------+
                 |
                 v
                RRF
                 |
                 v
             Top 5 Chunk
                 |
                 v
          去重与多样性处理
                 |
                 v
          关联文档及图片
                 |
                 v
           Context Builder
```

## 6.3 BM25 关键词检索

使用 Elasticsearch 的 BM25 算法进行关键词检索。

主要用于：

- 文档中的专有名词。
- 具体名称。
- 关键词匹配。
- 数字、编号和专业术语。

## 6.4 Dense Vector 向量检索

使用 BGE 模型将文本转换为向量。

模型：

`BAAI/bge-small-zh-v1.5`

用于查找语义相近的内容。

该模型输出向量维度为 512。

向量生成在 Mac 本地执行，向量存储和检索由 Elasticsearch 负责。

## 6.5 RRF 结果融合

将 BM25 检索结果和 Dense Vector 检索结果通过 RRF 融合。

RRF 用于综合不同检索方式的排名。

RRF 分数不等同于语义相似度，不直接将其作为语义相关性阈值。

## 6.6 Top K 与 Reranker

第一版：

- 最终保留 Top 5 Chunk。
- 不使用 Reranker。
- 不使用 Multi-Query。
- 不进行独立图片向量检索。

后续根据实际检索效果再决定是否引入更复杂的排序机制。

## 6.7 相关性不足的处理

当知识库没有提供足够依据时，系统应明确告知用户当前知识库缺乏足够信息。

允许模型结合通用知识回答，但不能伪造 PDF 来源和引用内容。

# 7. PDF 异步解析架构

## 7.1 技术选型

| 组件 | 技术 |
|---|---|
| 文件上传 | FastAPI |
| 任务状态 | SQLite |
| 消息传递 | Kafka |
| PDF 解析 | MinerU VLM API |
| Embedding | BGE |
| 检索存储 | Elasticsearch |
| 文件存储 | Mac 本地文件系统 |

## 7.2 PDF 上传流程

```text
用户选择 PDF
      |
      v
FastAPI 接收上传
      |
      v
文件格式与大小校验
      |
      v
保存到本地文件系统
      |
      v
SQLite 创建文档记录
      |
      v
SQLite 创建解析任务
      |
      v
投递 Kafka 消息
      |
      v
返回上传结果
```

PDF 上传成功后自动创建解析任务，不需要用户手动点击开始解析。

## 7.3 上传限制

| 项目 | 限制 |
|---|---|
| 支持文件类型 | PDF |
| 单文件最大大小 | 100 MB |
| 单次最大上传数量 | 10 个 |
| 上传方式 | 点击选择、拖拽上传 |
| 上传进度 | 支持 |
| 单文件失败处理 | 独立显示失败状态，允许重传 |

## 7.4 Kafka 消息设计原则

Kafka 只传递任务元数据，不传输 PDF 文件本身。

消息主要包含：

- task_id。
- document_id。
- version_id。
- 文件存储标识或路径。
- 任务类型。
- 必要的任务元数据。

消息结构、字段类型和版本管理将在核心数据结构设计阶段详细确定。

## 7.5 PDF Worker

PDF Worker 作为独立进程运行。

主要职责：

1. 消费 Kafka 消息。
2. 查询 SQLite 中的任务状态。
3. 检查任务是否已经处理。
4. 调用 MinerU API。
5. 获取 MinerU 解析任务标识。
6. 轮询解析状态。
7. 下载解析结果。
8. 保存解析产物。
9. 文本切分。
10. 调用 BGE 生成向量。
11. 写入 Elasticsearch。
12. 更新 SQLite 文档和任务状态。

## 7.6 MinerU 调用方式

PDF 解析使用 MinerU 云端 API，模型选择 VLM。

Worker 通过 API 提交 PDF 解析任务。

MinerU 返回任务标识后，Worker 保存对应的 batch_id，并通过异步轮询获取解析结果。

云端解析期间，该任务仍然占用一个解析并发名额。

## 7.7 解析并发限制

第一版 PDF 解析最大并发数为 2。

这里的并发指同时处于实际解析流程中的任务数量。

Worker 需要在任务调度层维护并发限制，不能因为多个 Kafka 消息同时到达而无限创建解析任务。

## 7.8 任务状态管理

文档状态包括：

- pending：待解析。
- processing：解析中。
- completed：解析完成。
- failed：解析失败。

SQLite 是任务状态和任务恢复的主要依据。

Worker 处理任务时，需要更新任务状态、开始时间、完成时间和错误信息。

## 7.9 异常处理和恢复

需要区分两种异常。

### 通信异常

例如：

- 网络中断。
- API 超时。
- 临时下载失败。
- 第三方服务暂时不可用。

这类问题允许有限次数自动重试。

### 解析失败

例如：

- MinerU 明确返回解析失败。
- PDF 文件损坏。
- 文件内容不符合解析要求。

这类问题不自动重新提交解析任务。

系统将任务标记为失败，用户可以手动重新解析。

## 7.10 Worker 异常恢复

Worker 异常退出后，重新启动时需要检查 SQLite 中未完成的任务。

恢复原则：

1. 查询尚未完成的任务。
2. 判断任务是否已经提交 MinerU。
3. 如果已有 batch_id，优先复用原有任务。
4. 不重复提交已经成功提交的 MinerU 任务。
5. 如果 Elasticsearch 写入成功但 SQLite 尚未更新，需要执行状态修复。
6. 对无法自动恢复的任务，记录错误并保留人工处理入口。

## 7.11 任务幂等

Kafka 可能重复投递消息，Worker 需要实现幂等处理。

幂等判断至少应结合：

- task_id。
- document_id。
- version_id。
- 当前任务状态。

重复消费不能导致重复创建解析任务，也不能让旧版本数据覆盖新版本数据。

# 9. 数据存储架构

## 9.1 数据存储技术选型

| 数据类型 | 存储技术 |
|---|---|
| 关系型业务数据 | SQLite |
| 文档全文检索 | Elasticsearch |
| 文档向量 | Elasticsearch |
| 异步任务消息 | Kafka |
| 原始文件 | Mac 本地文件系统 |
| 解析产物 | Mac 本地文件系统 |
| 用户上传图片 | Mac 本地文件系统 |

## 9.2 SQLite

SQLite 负责需要关系型管理的业务数据。

主要包括：

- 文档信息。
- 文档版本信息。
- 解析任务信息。
- 对话信息。
- 消息信息。
- 用户偏好。
- 系统操作日志。
- 必要的模型调用统计信息。

SQLite 不负责向量检索。

## 9.3 Elasticsearch

Elasticsearch 负责：

- 文档 Chunk 存储。
- BM25 全文检索。
- Dense Vector 存储。
- 向量相似度检索。
- 混合检索结果融合。

Elasticsearch 中的数据应能关联到 SQLite 中的文档和版本信息。

## 9.4 Kafka

Kafka 负责 PDF 解析任务的异步消息传递。

Kafka 不作为业务数据的最终存储来源。

任务是否完成、任务属于哪个文档、任务当前处于什么状态，以 SQLite 中的业务记录为主要依据。

## 9.5 文件系统

Mac 本地文件系统保存：

1. 原始 PDF。
2. MinerU 解析产物。
3. Markdown 文件。
4. JSON 文件。
5. PDF 提取图片。
6. 用户上传图片。

文件内容不直接存储在 SQLite 中，通过文件路径或存储标识进行关联。

## 9.6 数据生命周期

| 数据 | 存储位置 | 生命周期 |
|---|---|---|
| 原始 PDF | 本地文件系统 | 文档删除时清理 |
| 解析 Markdown | 本地文件系统 | 解析版本切换或文档删除时清理 |
| 解析 JSON | 本地文件系统 | 解析版本切换或文档删除时清理 |
| PDF 提取图片 | 本地文件系统 | 随解析版本管理 |
| 用户上传图片 | 本地文件系统 | 随消息生命周期管理 |
| 文档和任务记录 | SQLite | 按业务规则管理 |
| 对话和消息 | SQLite | 用户删除时清理 |
| Chunk 和向量 | Elasticsearch | 随文档版本管理 |

PDF 提取图片和用户上传图片必须分开管理，不能混用生命周期。

## 9.7 文档版本管理

重新解析时：

1. 保留旧版本。
2. 创建新解析版本。
3. 新版本独立解析和写入 Elasticsearch。
4. 新版本解析成功后，切换为有效版本。
5. 切换成功后清理旧版本文件和索引。
6. 新版本解析失败时，旧版本继续可用。

历史解析任务的状态、开始时间、完成时间和错误日志保留。

旧版本解析文件不长期保留。

## 9.8 删除文档

删除文档时，需要清理：

- 原始 PDF。
- 解析产物。
- 提取图片。
- Elasticsearch 对应索引数据。
- 文档相关业务记录。

如果文档正在解析，需要阻止旧任务继续写入 Elasticsearch。

应通过文档删除状态、版本标识和任务状态校验避免并发写入造成数据残留。

## 9.9 一键清空知识库

第一版支持一键清空知识库。

操作需要二次确认。

清空知识库时清理文档及其解析产物和检索数据，但保留历史对话。

# 11. 数据一致性与异常恢复

## 11.1 数据职责边界

系统涉及多个存储组件，需要明确它们之间的职责：

| 组件 | 数据职责 |
|---|---|
| SQLite | 业务状态和任务恢复的主要依据 |
| Kafka | 异步任务传递 |
| Elasticsearch | 可重建的检索数据 |
| 文件系统 | 原始文件和解析产物 |

Elasticsearch 不作为文档业务状态的唯一来源。

Kafka 消息也不作为任务最终状态的唯一来源。

## 11.2 SQLite 与 Kafka 一致性

SQLite 和 Kafka 之间不存在跨系统原子事务。

因此，任务创建和消息投递需要设计失败恢复机制。

建议采用轻量级待投递任务记录：

1. SQLite 创建任务时记录待投递状态。
2. Kafka 投递成功后更新投递状态。
3. 投递失败时保留待投递记录。
4. 应用或恢复任务定期扫描待投递记录。
5. 对尚未成功投递的任务重新发送消息。
6. Worker 通过 task_id 和任务状态保证幂等。

具体是否采用独立 Outbox 表，在数据库结构设计阶段确定。

## 11.3 Elasticsearch 与 SQLite 一致性

Elasticsearch 写入成功不代表 SQLite 状态已经更新。

因此，Worker 在执行完成阶段需要：

1. 确认目标版本的数据已经写入。
2. 检查文档是否仍然有效。
3. 更新 SQLite 任务状态和文档状态。
4. 如果状态更新失败，恢复时重新检查 Elasticsearch 数据并修复状态。

检索数据应具备明确的 document_id 和 version_id 标识，避免不同版本互相覆盖。

## 11.4 删除与任务并发

用户删除文档时，需要防止正在运行的 Worker 继续写入数据。

建议：

- 删除操作先更新 SQLite 文档状态。
- Worker 在关键写入阶段检查文档和版本状态。
- 已被删除的文档不允许继续提交有效检索数据。
- 清理 Elasticsearch 和本地文件。
- 清理过程需要能够安全重复执行。

## 11.5 错误处理原则

所有异常应尽可能区分：

- 可重试异常。
- 不可重试异常。
- 需要人工干预的异常。

对于自动重试，应设置次数和边界，避免无限重试。

# 12. 安全与监控

## 12.1 API 访问安全

第一版为个人使用，不实现完整的多用户注册登录系统。

但需要提供简单的访问认证，保护前端页面和后端 API。

API Key 不得暴露给浏览器。

## 12.2 第三方 API 密钥管理

以下密钥由后端维护：

- MinerU API Key。
- DeepSeek API Key。

通过后端配置文件或环境变量加载。

不通过前端接口返回明文密钥。

## 12.3 Elasticsearch 和 Kafka 安全

Linux 服务不直接向公网开放不必要的访问端口。

Mac 通过 SSH 加密隧道访问。

Elasticsearch 使用认证和 HTTPS 等必要的安全配置。

Kafka 使用受保护的网络访问方式和必要的认证机制。

## 12.4 系统健康检查

系统提供健康检查页面。

检查对象：

- MinerU。
- DeepSeek。
- Kafka。
- Elasticsearch。
- SQLite。

支持：

1. 后台定时检查。
2. 手动检查单个依赖。
3. 手动检查全部依赖。
4. 显示最近检查时间。
5. 展示检查结果和异常信息。

应用启动时不自动检查全部依赖。

## 12.5 操作日志

记录基础系统操作日志。

日志包括必要的操作时间、操作类型、操作对象和执行结果等信息。

日志保留最近 90 天，超过期限自动清理。

第一版不支持日志下载和导出。

## 12.6 模型调用统计

第一版统计：

- 问答次数。
- 回答数。
- Token 总量。
- LLM 失败次数。

不进行模型费用估算。

模型调用统计数据应尽可能从实际模型响应中获取，无法获取的字段应允许为空或标记为不可用，不通过估算伪造精确值。

# 17. 总结

本项目第一版采用前后端分离、模块化单体后端、独立 PDF Worker 和多存储组件协作的总体架构。

核心技术选型：

- 前端：React + TypeScript + Vite。
- 后端：Python + FastAPI。
- AI 框架：LangChain。
- 大语言模型：DeepSeek Flash。
- Embedding：BGE Small Chinese。
- 业务数据库：SQLite。
- 检索数据库：Elasticsearch。
- 消息队列：Kafka。
- PDF 解析：MinerU VLM API。

核心设计思想：

1. SQLite 管理业务数据和任务状态。
2. Elasticsearch 负责 BM25 和 Dense Vector 检索。
3. Kafka 负责异步 PDF 任务传递。
4. Worker 独立处理 PDF 解析。
5. LangChain 负责模型调用相关能力。
6. Python 代码控制完整 RAG 工作流。
7. 文件系统负责原始 PDF 和解析产物存储。
8. SSH 隧道保护 Mac 与 Linux 之间的服务通信。

第一版不追求复杂的 Agent 和分布式架构，而是优先实现一条可靠、完整、可维护的多模态 RAG 业务链路。

# SQL Code Agent（LangChain）技术实现文档

## 1. 文档目的

本文定义 `langchain-agent` 的实现方案。项目参考同级 `openai-agent` 的业务目标、七阶段流程、安全边界和验收题，使用 LangChain 负责模型调用与结构化输出，使用 LangGraph 负责确定性工作流编排。

实现目标：

- 将中文自然语言问题转换为 SQLite 查询，并基于 `data/chinook.db` 返回中文答案。
- 明确执行数据库解析、Table 选择、SQL 生成、SQL 校验、SQL 改写、SQL 执行、结果汇总七个业务阶段。
- Q1–Q22 验证查询结果；Q23–Q25 验证危险请求被拒绝且数据库不发生变化。
- 模型仅承担语义判断与文本生成；Python 掌控 SQL 安全、数据库权限、资源限制和重试次数。
- 普通单元测试不调用真实模型，真实模型验收必须显式启用。

不在本期范围内：

- 多轮对话记忆和跨请求状态持久化。
- 让模型自主选择或调用数据库工具。
- 写入、建表、数据库管理或数据导出能力。
- 向量数据库、RAG、Web UI 和服务端 API。

## 2. 技术选型

### 2.1 核心组件

- Python 3.12
- LangChain：Prompt、Chat Model、结构化输出和 Runnable 调用
- LangGraph：七阶段状态图、条件路由和有限重试
- `langchain-openai`：OpenAI 及 OpenAI-compatible Provider 适配
- Pydantic 2：配置和阶段输入输出契约
- SQLite：Schema 解析、只读预检和查询执行
- pytest / pytest-asyncio：单元测试和异步集成测试

具体依赖版本统一固定在 `pyproject.toml`，本文不重复维护版本号。

### 2.2 LangChain 使用原则

四个模型能力分别实现为结构化 Runnable：

- `table_selector_chain`
- `sql_generator_chain`
- `sql_rewriter_chain`
- `answer_synthesizer_chain`

每条链由 `ChatPromptTemplate`、Chat Model 和 `with_structured_output(PydanticModel)` 组成，通过 `ainvoke()` 调用。

本项目不使用 `create_agent`、模型工具调用或 handoff。原因是七阶段顺序、安全短路和重试上限必须由代码确定，模型不能自行决定是否校验或执行 SQL。

LangGraph 只负责编排，不替代安全组件。图在工作流实例创建时编译一次，每个问题使用独立初始状态执行。

### 3.2 模块职责

- `config.py`：集中读取和校验环境变量，解析数据库绝对路径。
- `models.py`：Pydantic 阶段契约、查询结果、校验结果和对外响应。
- `schema_service.py`：读取并缓存 Schema、外键、行数和脱敏样本。
- `sql_safety.py`：SQL 标准化、词法检查、SQLite authorizer 和编译预检。
- `query_executor.py`：在独立只读连接中执行 SQL，并限制结果行数和执行步数。
- `chains.py`：四条 LangChain 结构化模型链及 `ModelGateway` 抽象。
- `graph.py`：LangGraph 状态定义、节点函数、条件路由和图编译。
- `workflow.py`：对外工作流门面，创建 request ID、调用图并映射稳定错误。
- `cli.py`：命令行参数、日志初始化、退出码和用户可见错误。

### 3.3 依赖方向

```text
CLI
 └── Workflow facade
      └── Compiled LangGraph
           ├── ModelGateway ── LangChain structured Runnables
           ├── SchemaService
           ├── SqlSafetyValidator
           └── ReadOnlyQueryExecutor
```

`graph.py` 依赖各能力接口，各基础组件不得反向依赖 LangGraph。这样可以独立测试安全层和执行层，也可以用 Fake Gateway 替换真实模型。

## 4. 数据契约与状态

### 4.1 模型结构化输出

```python
class TableSelection(BaseModel):
    tables: list[str]


class SqlDraft(BaseModel):
    sql: str


class FinalAnswer(BaseModel):
    answer: str
```

Pydantic 字段应提供清晰描述，供模型的结构化输出 Schema 使用。模型返回值必须再次经过 Python 类型检查；解析失败统一转换为 `ModelContractError`，不得从非结构化文本中用正则猜测 JSON。

### 4.2 图状态

使用 `TypedDict` 定义 LangGraph 状态，使用 Pydantic 定义边界对象：

```python
class SqlAgentState(TypedDict, total=False):
    request_id: str
    question: str
    catalog: SchemaCatalog
    selection_context: str
    selected_tables: list[str]
    focused_schema: str
    sql: str
    validation: ValidationResult
    query_result: QueryResult
    rewrite_count: int
    failed_sql: list[str]
    final_answer: str
    refusal_reason: str
    error_code: str
```

图中没有并行写入同一字段的节点，因此不需要 reducer。节点只返回本节点修改的字段，不原样复制完整状态。

`catalog` 仅在当前请求内使用；查询结果和用户问题不跨请求持久化。当前版本不配置 checkpointer。

## 5. LangGraph 工作流

### 5.1 图节点

七个业务节点：

1. `parse_database`
2. `select_tables`
3. `generate_sql`
4. `validate_sql`
5. `rewrite_sql`
6. `execute_sql`
7. `synthesize_answer`

辅助终止节点：

- `refuse_request`：生成固定的安全拒绝结果，不调用模型。
- `fail_request`：根据稳定错误码结束流程，由门面层转成异常。

辅助节点不是新增业务阶段，只承担图的终止语义。

### 5.2 路由

```text
START
  → parse_database
  → select_tables
  → generate_sql
  → validate_sql
      ├─ OK → execute_sql
      │        ├─ success → synthesize_answer → END
      │        ├─ repairable → rewrite_sql
      │        ├─ timeout → fail_request → END
      │        └─ safety error → fail_request → END
      ├─ SYNTAX_ERROR / SCHEMA_ERROR
      │        ├─ budget available → rewrite_sql → validate_sql
      │        └─ budget exhausted → fail_request → END
      └─ SAFETY_VIOLATION / MULTI_STATEMENT
               → refuse_request → END
```

关键不变量：

- `generate_sql` 后必须进入 `validate_sql`。
- `rewrite_sql` 后必须重新进入 `validate_sql`，不能直接执行。
- 安全违规和多语句错误不能进入改写，防止模型改变危险请求的含义。
- `execute_sql` 使用与预检不同的连接，并重新安装全部只读限制。
- 只有成功获得 `QueryResult` 才能进入结果汇总。

### 5.3 条件路由函数

路由函数必须是无副作用的纯函数，只读取状态并返回固定路由名：

- `route_after_validation`
- `route_after_execution`
- `route_after_rewrite_budget`

所有可能返回值在 `add_conditional_edges()` 中显式声明，避免运行期跳转到未知节点。

### 5.4 重试策略

- Table 选择最多调用两次；首次结果包含非法表名、为空或超过 6 张表时，将具体错误反馈加入第二次 Prompt。
- SQL 改写次数由 `SQL_AGENT_MAX_REWRITES` 控制，默认 2，最大 5。
- `failed_sql` 保存标准化后的失败 SQL；模型返回历史中已经出现的 SQL 时立即终止。
- 只对 `SYNTAX_ERROR`、`SCHEMA_ERROR` 和执行阶段可修复的 SQLite 错误进行改写。
- API 超时、鉴权、限流等模型调用错误不在图内无限重试。若需要网络重试，应在 Gateway 层配置较小且明确的重试次数，并记录最终错误类型。

## 6. 四条模型链

### 6.1 模型初始化

Gateway 根据配置初始化一次 Chat Model。OpenAI-compatible Provider 使用 OpenAI 模型适配器并传入自定义 `base_url`；密钥通过参数或环境变量提供，不进入 Prompt、状态日志和异常文本。

模型公共设置：

- `temperature=0`
- 明确的请求超时
- 较小且有限的 Provider 网络重试
- 各链独立系统 Prompt
- 每次调用携带 `request_id`、阶段名和 Prompt 版本等 metadata

Provider 必须实际支持当前结构化输出方式。若 Provider 不兼容，启动后的首次真实调用应抛出清晰的 `ModelContractError`；不增加单独的付费探测请求。

### 6.2 Table 选择链

输入：

- 原始问题
- 轻量数据库目录：表名、字段名、行数和外键
- 可选的上一次无效结果反馈

输出：`TableSelection`

Python 后置校验：

- 只能包含目录中的精确表名。
- 去重后必须为 1–6 张表。
- 任一非法表名使整次输出失败，不能静默丢弃。

### 6.3 SQL 生成链

输入：

- 原始问题
- 已选表的详细 Schema
- 脱敏样本

输出：`SqlDraft`

Prompt 约束：

- 只输出一条 SQLite SQL，不输出 Markdown。
- 普通查询只能使用 `SELECT` 或只读 `WITH`。
- 字段和表必须来自输入 Schema。
- 排名问题必须使用确定性 `ORDER BY`。
- 正确处理 NULL、日期、金额、聚合和关联关系。
- 若原始问题要求写入或建表，忠实表达原意，由确定性安全层拒绝；不能悄悄改成无害查询。

### 6.4 SQL 改写链

输入：

- 原始问题
- 当前 SQL
- SQLite 错误分类和消息
- 已选表 Schema
- 历史失败 SQL

输出：`SqlDraft`

改写只能修复语法或 Schema 问题，不得删除关键筛选条件、扩大查询含义或引入写操作。

### 6.5 结果汇总链

输入：

- 原始问题
- 最终 SQL
- 列名
- 查询结果
- 行数和截断标记

输出：`FinalAnswer`

要求：

- 查询结果是唯一事实来源，不补充常识或猜测。
- 专有名词和数值保持准确。
- 空结果明确回答“没有”或“0”。
- 金额保留两位小数并注明单位。
- 结果被截断时必须说明。
- 除非用户明确要求，不展示 SQL。

## 7. Schema 服务

`SchemaService` 从以下来源构建目录：

- `sqlite_master`
- `PRAGMA table_info`
- `PRAGMA foreign_key_list`
- 每张表的行数
- 每张表最多两条样本

样本中的 `Email`、`Phone`、`Fax`、`Address` 在发送给模型前替换为 `[REDACTED]`，但保留 NULL 信息。

目录按数据库文件 `mtime_ns` 缓存。Table 选择只接收轻量目录；SQL 生成和改写只接收已选表的详细 Schema，减少 token 和无关上下文。

标识符必须使用安全引用函数处理，数据库相对路径必须相对项目目录解析，不能依赖命令执行时的当前目录。

## 8. SQL 安全设计

安全层延续参考项目的纵深防御，不能以 LangChain Prompt 或 SQL 工具包替代。

### 8.1 静态检查

1. 清理模型偶尔附带的单层 Markdown SQL 围栏。
2. 检查原始问题中的明显写入、建表和导出意图。
3. 词法遮蔽字符串、引用标识符及行/块注释。
4. 首关键字只能是 `SELECT` 或 `WITH`。
5. 只允许单条语句，可接受唯一的句末分号。
6. 拒绝 DML、DDL、`ATTACH`、`DETACH`、`PRAGMA`、`VACUUM` 等关键字。

### 8.2 SQLite 编译预检

在只读连接上执行：

- SQLite URI `mode=ro`
- `PRAGMA query_only = ON`
- 安装 SQLite authorizer
- `EXPLAIN QUERY PLAN <sql>`

预检只解析语法和对象引用，不运行用户查询。校验结果分类：

- `OK`
- `SAFETY_VIOLATION`
- `MULTI_STATEMENT`
- `SYNTAX_ERROR`
- `SCHEMA_ERROR`

### 8.3 只读执行

`ReadOnlyQueryExecutor` 在独立连接上再次启用：

- SQLite URI `mode=ro`
- `PRAGMA query_only = ON`
- SQLite authorizer
- progress handler 执行步数上限
- 返回行数上限

执行时读取 `MAX_RESULT_ROWS + 1` 行；多出的一行仅用于计算 `truncated`，不发送给总结链。预检和执行重复设置防线是必要的纵深防御。

`Settings.from_env()` 负责：

- 将数据库路径转换成绝对路径并验证文件可读。
- 根据 Provider 选择 API Key 和默认 `base_url`。

`.env` 必须加入 `.gitignore`。

## 10. 错误处理与可观察性

### 10.1 稳定错误

对外保持稳定错误类型和中文消息：

- `InvalidTableSelection`
- `ModelContractError`
- `QueryGenerationFailed`
- `QueryTimedOut`
- `UnsafeExecutionBlocked`
- `ConfigurationError`

内部异常不得直接向 CLI 暴露 API Key、Provider 原始响应或客户数据。用户消息附带短错误 ID，完整堆栈仅写本地调试日志。

### 10.2 日志

每个节点记录结构化事件：

- `request_id`
- 节点名和开始/结束状态
- 选中表名
- SQL 和校验类别
- 实际读取表
- 改写次数
- 执行耗时、结果行数和截断状态
- Prompt 版本

日志不得记录 API Key、未脱敏样本或完整查询结果。

### 10.3 Tracing

Tracing 直接由 LangSmith 官方环境变量控制：`LANGSMITH_TRACING` 未设置或为 `false` 时不上报；trace 目标由 `LANGSMITH_AGENT_ID` 和 `LANGSMITH_AGENT_ENVIRONMENT` 确定，不能与 `LANGSMITH_PROJECT` 同时设置。工作流根 run 名为 `sql_agent_workflow`，metadata 包含 request ID、Provider 和模型名；各模型调用作为子 run，携带 run name、tag 和 Prompt 版本。

启用外部 tracing 前必须确认数据治理要求；用户问题、Schema 样本和查询结果可能成为 trace 内容。即使 tracing 开启，密钥也不得进入 metadata。

## 11. 测试方案

### 11.1 单元测试

普通测试不得访问模型 API：

- `test_schema_service.py`：表、列、外键、行数、缓存和样本脱敏。
- `test_sql_safety.py`：只读 SQL、危险关键字、注释/字符串遮蔽、多语句和 Schema 错误。
- `test_query_executor.py`：列名、NULL、空结果、截断、超时和执行期写入拒绝。
- `test_graph.py`：正常路由、选表重试、改写后重验、重试耗尽和安全短路。

模型相关测试注入 `FakeModelGateway`，按顺序返回 Pydantic 对象，并记录调用阶段。测试必须证明：

- 安全请求按顺序调用选择、生成和汇总。
- Schema 错误调用一次改写并重新校验。
- 安全违规不调用执行器、改写链或汇总链。
- 重复失败 SQL 提前终止。
- 图的每次调用使用独立状态。

### 11.2 真实模型验收

沿用参考项目 25 个问题：

- Q1–Q22：检查答案包含预期关键事实。
- Q23–Q25：检查回答包含“拒绝”，并比较执行前后的数据库 SHA-256、表数量和关键表行数。

真实模型验收通过环境变量显式开启：

```bash
RUN_SQL_AGENT_INTEGRATION=1 python -m pytest -m integration
```

默认跳过集成测试，避免意外费用和外部依赖导致普通测试不稳定。

## 13. 验收标准

- 七个业务阶段在代码和日志中可独立观察。
- 所有模型输出均经过 Pydantic 结构化验证。
- SQL 改写后必定重新校验，且重试次数有硬上限。
- Q23–Q25 不进入执行器，数据库快照保持不变。
- 数据库连接在预检和执行阶段均为只读。
- 普通测试不需要 API Key 且全部通过。
- 真实模型验收覆盖 22 个读取问题和 3 个危险请求。
- DeepSeek 和 OpenAI 至少各有清晰的配置路径；不兼容的结构化输出能产生可诊断错误。

## 14. 关键取舍

保留：

- 七阶段显式状态图，而不是单个 SQL Agent。
- 四个职责单一的结构化模型链。
- Gateway 抽象和 Fake 实现，保证无费用测试。
- 多层 SQL 安全、结果上限和执行步数上限。

暂不采用：

- LangChain SQLDatabaseToolkit：其工具自治模式会扩大模型权限面，且不能替代当前 SQLite authorizer 和只读执行器。
- LangGraph checkpointer：当前是单次问答，没有恢复或跨轮会话需求。
- 模型驱动路由：安全分类和重试条件应由确定性代码决定。
- 非结构化 JSON 降级解析：会掩盖 Provider 兼容问题并削弱契约。

该方案使用 LangChain 提供模型抽象与结构化输出，使用 LangGraph 提供显式、可测试的流程编排，同时保持数据库安全边界完全由本地确定性代码控制。

## 一、 我们到底要实现什么？（核心目标与确定项）

### 1. 最终要做出个什么东西？

用一句话说：**做一个“懂音乐商店账目”的数据问答机器人。**

* **输入（人话）**：用户输入一句普通的问题，比如：*“在咱们店里，哪个国家的客户买音乐花钱最多？”*
* **黑盒处理（你的程序）**：你的程序自己去查数据库、算账。
* **输出（人话）**：程序回答：*“消费最高的是美国（USA）客户，累计消费了 523.06 美元。”*

### 2. 哪些事情是已经完全确定的？（已知条件）

1. **数据源确定（`chinook.db`）**：这是一个现成的、单文件的 SQLite 数据库（不需要你装 MySQL 服务，Python 自带的 `sqlite3` 库就能直接打开）。它模拟了一家像 iTunes 一样的数字音乐商店，里面固定只有 **11 张表**（比如：`customers` 客户表、`invoices` 账单表、`tracks` 歌曲表、`artists` 歌手表等）。
2. **核心帮手确定（大语言模型 LLM）**：你自己不需要提前写死任何 SQL 语句，而是让大模型帮你把“用户的提问”翻译成“SQL 代码”。
3. **运转流程确定（7 个步骤）**：作业题目已经帮你规定好了程序内部必须走完的 7 个环节（数据库解析 $\rightarrow$ 选表 $\rightarrow$ 写 SQL $\rightarrow$ 检查 SQL $\rightarrow$ 改错 $\rightarrow$ 运行 SQL $\rightarrow$ 总结回答）。

---

## 二、 为什么作业要定这 7 个步骤？（一步步推导演化）

你可能会问：*“既然有大模型，我直接把用户问题丢给大模型，让它写个 SQL，我放到数据库里一跑，不就完事了吗？为什么要搞 7 步这么麻烦？”*

我们顺着这个最简单的想法往下走，看看每走一步会撞上什么南墙，你就能彻底明白这 7 个步骤是怎么来的了：

### 阶段 1：让大模型认识数据库（前 2 步的由来）

* **最初的想法**：直接问大模型：“哪个国家的客户花钱最多？帮我写个 SQL。”
* **撞墙 1（瞎编乱造）**：大模型根本不知道你的 `chinook.db` 里有哪些表、字段叫什么名字。它会瞎编出 `SELECT country FROM user_orders`，放到你的数据库里根本跑不通。
* **👉 诞生第 1 步：【数据库解析】**
* **这一步干嘛**：在一切开始前，用 Python 代码把 `chinook.db` 翻个底朝天——查清楚里面有哪 11 张表、每张表有哪些列名（字段）、随便抽两行真实数据看看长什么样，整理成一份“数据库说明书”。


* **继续往下走**：有了“数据库说明书”，我把 11 张表的说明书全都塞给大模型，让它写 SQL。
* **撞墙 2（信息过载与干扰）**：用户明明只问“客户花钱最多”，其实只需要看 `customers`（客户表）和 `invoices`（账单表）。但你把员工表、歌单表、流派表全塞给大模型，不仅浪费钱（Token），大模型还容易看花眼，把不相干的表胡乱连在一起。如果以后数据库有 200 张表，根本塞不进去。
* **👉 诞生第 2 步：【Table 选择（选表）】**
* **这一步干嘛**：先让大模型看一眼“目录”（只有 11 张表的名字），问它：“要回答用户这个问题，你觉得只需要用到哪几张表？”大模型挑出 `customers` 和 `invoices` 后，我们再只把这两张表的详细说明书给它。



---

### 阶段 2：写出代码并确保它能跑通（中间 3 步的由来）

* **继续往下走**：现在大模型拿到了精选出来的 2 张表说明书，开始写 SQL 了。
* **👉 诞生第 3 步：【SQL 生成】**
* **这一步干嘛**：大模型根据用户问题和挑出来的表结构，写出第一版 SQL 语句（比如：`SELECT BillingCountry, SUM(Total) FROM invoices GROUP BY BillingCountry...`）。


* **继续往下走**：拿到大模型写的 SQL，我能直接丢进数据库运行吗？
* **撞墙 3（语法写错 / 恶意删库）**：大模型有时候会犯糊涂，比如把字段名拼错、括号少写半边，或者遇到调皮的用户输入“帮我把所有账单表删掉”，大模型真写了个 `DROP TABLE invoices`。
* **👉 诞生第 4 步：【SQL 校验（检查）】**
* **这一步干嘛**：像安检员一样，在真正查数据之前拦一下。检查两点：① 有没有删库、改数据的危险词？② 语法对不对、字段名存不存在？如果检查通过，放行；如果不通过，记录下“错在哪了”。


* **继续往下走**：万一第 4 步检查出语法错了（比如大模型写了个不存在的字段名 `CountryName`），程序直接报错退出吗？
* **撞墙 4（一次出错就罢工，太脆弱）**：人写代码还会报错呢，看见报错改一下就好了，程序也应该有“知错能改”的能力。
* **👉 诞生第 5 步：【SQL 改写（改错）】**
* **这一步干嘛**：当第 4 步检查不通过时，把“刚才写错的 SQL” + “报错原因”一起退回给大模型，跟它说：“你刚才写的 SQL 报错了，原因是没有 `CountryName` 这个字段，请看着表结构重新写一个！”改好后，再送回第 4 步检查。



---

### 阶段 3：拿到数据并说人话（最后 2 步的由来）

* **继续往下走**：SQL 终于通过了第 4 步的检查，语法完全正确、也很安全。
* **👉 诞生第 6 步：【SQL 执行】**
* **这一步干嘛**：真正用 Python 连接 `chinook.db`，运行那条正确的 SQL 语句，从数据库里把干巴巴的数据捞出来（比如捞出来一个列表：`[('USA', 523.06)]`）。*（注：万一运行的时候还是报错了，也可以退回第 5 步重改）*。


* **继续往下走**：把 `[('USA', 523.06)]` 直接打印给用户看吗？
* **撞墙 5（体验差，看不懂）**：不懂技术的用户看到括号和引号一脸懵，不知道 `523.06` 是人数还是金额。
* **👉 诞生第 7 步：【结果汇总】**
* **这一步干嘛**：把【用户最初的问题】和【第 6 步捞出来的干巴巴的数据】一起交给大模型，让它用通顺、礼貌的人话总结出来：“根据查询，消费最高的国家是美国（USA），总金额为 523.06。”
